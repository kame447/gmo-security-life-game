# ブランチ戦略

ブランチの種類と命名規則、作業からマージまでの流れを定めます。

## メインブランチ

- **main**：常に安定した状態を保つブランチです。直接 push せず、変更はプルリクエストを通じてのみマージします。

現在は `develop` ブランチを置かず、作業ブランチは `main` から分岐して `main` にマージします。リリース用の統合ブランチが必要になった時点で見直します。

## 命名規則

作業ブランチは `<種類>/<内容>` の形で名付けます。

- `<種類>` は下の表の接頭辞から選ぶ。
- `<内容>` は英小文字・数字・ハイフンだけで、作業内容が分かる短いキーワードにする（例：`player-sprite`）。
- 日本語、スペース、アンダースコア、大文字は使わない。
- 一つのブランチでは一つの目的だけを扱う。目的が複数ある場合はブランチを分ける。

| 接頭辞 | 目的 | 例 |
|---|---|---|
| `feat/` | 新しい機能、既存機能の大きな改善、ゲーム素材の追加 | `feat/life-progress`, `feat/player-sprite` |
| `fix/` | バグの修正 | `fix/login-error`, `fix/broken-link` |
| `docs/` | ドキュメントの作成・更新 | `docs/update-readme`, `docs/branch-naming-rules` |
| `ci/` | CI の設定ファイルやスクリプトの変更 | `ci/add-linting`, `ci/update-pipeline` |
| `infra/` | インフラ構成（`infra/` 配下の Terraform など）の変更 | `infra/remote-state`, `infra/add-waf` |
| `refactor/` | 外部から見える挙動を変えないコード構造の改善 | `refactor/cleanup-service` |
| `style/` | フォーマットやコーディング規約への準拠のみの変更 | `style/fix-indentation`, `style/apply-lint-rules` |
| `test/` | テストの追加・修正 | `test/add-event-tests` |
| `chore/` | 上記に当てはまらない雑多な変更（`.gitignore`、依存関係の更新など） | `chore/update-gitignore` |
| `poc/` | 採用前の技術検証。そのままマージせず、採用時は内容を見直したうえで正式な種類のブランチで取り込む | `poc/aws-infra` |

## 開発フロー

1. **分岐**：最新の `main` から作業ブランチを作る。

   ```sh
   git switch main
   git pull
   git switch -c feat/player-sprite
   ```

2. **開発**：コード、テスト、関連ドキュメントの更新をブランチ内で行う。コミットは小さな単位に分け、内容が分かるメッセージを付ける。
3. **定期的な更新**：作業中に `main` が更新されたら、リベースまたはマージで取り込み、衝突を早めに解消する。
4. **プルリクエスト**：CI が通ったら `main` 宛てにプルリクエストを作る。説明には変更の目的、概要、確認方法、注意点を書く。
5. **レビューとマージ**：チームメンバーのレビューで承認されたらマージする。履歴を整理するため、スカッシュマージを推奨する。

## ブランチの整理

- マージ済みのブランチは削除する。
- 使われなくなった古いブランチは定期的に見直して削除する。
- この規則より前に作られたブランチ（`add-ci`、`test` など）は改名せず、マージ済みのものから順に削除する。
