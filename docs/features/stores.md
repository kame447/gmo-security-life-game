# 店舗の接続契約と現状棚卸し

[Issue #33](https://github.com/kame447/gmo-security-life-game/issues/33) は、商店・飲食店に屋外から入れる店内、探索通路、店員との会話、屋外への帰還地点を用意する要件。売買の会話・商品・資産更新は [#21](https://github.com/kame447/gmo-security-life-game/issues/21) の担当範囲とする。

この文書と `feat/store-contract` は、main `b219414` の読み取り棚卸し、既存コンビニの接続データ、検証、回帰仕様を扱う。店内やNPCを追加した実装ではない。買い物画面の試作の採用・UI承認とも別の成果物であり、#33の全店舗対応は未完了。

## データ契約

`game/src/data/stores.ts` の `StoreContact` は次の文字列参照を持つ。買い物試作の同名の型と同じ構造であり、そのUIを取り込む依存はない。

| フィールド | 解決する対象 |
| --- | --- |
| `storeId` | 店舗レコードの一意なID。現存レコードでは施設ID `shop-konbini` を使用。今後の命名方式は未決定 |
| `interiorAreaId` | `World.areas.get(id)` で解決する屋内エリア |
| `entrancePortalId` | 全エリアの `AreaRuntime.def.portals[].id` から一意に解決する入口 |
| `clerkEventKey` | 指定店内の `AreaRuntime.interactions` 内にあるNPCの `eventKey` |
| `catalogId` | #21側のカタログを参照する文字列。ここでは解決・商品定義・価格設定をしない |

レコードは現存コンビニの1件だけを持つ。`storeForClerk(areaId, eventKey)` は店内エリアと店員キーの**両方**が一致したレコードを返す。屋外の店先、棚、別室で同じキーを調べてもコンビニのレコードとして解決しない。カタログ本体やUIはこの契約に依存できるが、この契約はそれらに依存しない。

`game/src/stores/validate.ts` の純粋関数 `validateStoreContacts(world, records)` は問題の `{ storeId, code }[]` を返し、ワールドやレコードを変更しない。

| code | 判定 |
| --- | --- |
| `duplicate-store` | `storeId` の重複 |
| `duplicate-clerk-contact` | `(interiorAreaId, clerkEventKey)` の重複。同じ店員イベントを複数店舗へ結び付けない |
| `missing-interior`／`not-indoor` | 店内エリアがない／屋内ではない |
| `missing-entrance`／`ambiguous-entrance` | 入口IDがない／複数エリアを通じて重複する |
| `invalid-entrance` | 入口が屋外から始まらない、または指定店内へ着かない |
| `missing-return` | 指定店内から入口側の同じ屋外エリアへ戻るポータルがない |
| `missing-clerk`／`ambiguous-clerk`／`not-npc` | 店内にキーがない／複数対象に一致する／一致対象がNPCではない |

この関数は接続関係だけを検証する。全マップのID・座標・衝突・到達性は既存の `validateWorld()` と経路テストで確認する。帰還先のタイル・向きは実コンビニの往復回帰で照合する。任意の店内配置を正しいと保証する関数ではなく、カタログの存在や商品の取引も確認しない。

検証には呼出側が対象ワールドを明示する。現状棚卸しは `buildWorld()` の既定値。年代差分で入口や店員を意図的に無効化した場合、同じレコードを渡すと欠落として報告する。将来の店舗の開閉条件や、無効時にレコードをどう選ぶかは別途仕様化する。

## 追加手順の提案／要検証

正式な店舗ID・内装・名称・NPCの決定はマップ／NPC担当者と利用者が行う。次は決定前に作業分担と検査点を確認するための手順案であり、今回の実装で採用を決めたものではない。

1. マップ／NPC担当が対象施設を棚卸し表と照合する。未紐付けのcafe外観については、名称・施設への紐付け・既存店舗との関係を先に確認する。
2. マップ担当が施設、屋内エリア、屋外入口、屋外への出口を定義し、NPC担当が店内の店員とイベントキー、既定の名前・台詞を管理する。現在の物件は読み取り対象のままとし、このブランチでは変更しない。
3. マップ担当がデータだけの `stores.ts` に `StoreContact` を追加する案。#21担当が別ファイルにカタログを持ち、`catalogId` の参照先を調整する。編集前の予約・連絡を行い、同じファイルを同時編集しない。カタログをこのファイルに埋め込まない。
4. `stores.md` と `tests/fixtures/stores.ts` の分類を根拠とともに更新する。店内や入口が追加された店舗を「店内未対応」のままにすると回帰テストが失敗し、レコード・分類の更新を促す。
5. 接続検証、一般ワールド検証、入口→店員の隣→出口の経路、話しかける向き、帰還タイル・向き・保存復帰を確認する。新しい店内の通路・棚前もマップ担当のテストに追加する。

命名方式にも未決定事項がある。

| 選択肢（提案／要検証） | 現状から確認できる根拠と検討点 |
| --- | --- |
| 施設IDをstoreIdとし、店内・入口IDに関連する名前を付ける方式 | 現コンビニは施設 `shop-konbini`、店内 `shop-konbini-interior`、入口 `konbini-enter`。既存値を使えるが、施設未紐付けの外観や同種の複数店舗を区別する規則は別途必要 |
| 店舗IDを施設IDとは独立させ、接続先のエリア・入口を明示する方式 | 現在の型は参照先を文字列で明示するため、施設IDとの同一性を前提にしない。施設と店舗の対応管理が別途必要 |

どちらも未採用。座標由来の配置物ID、GUI表示用の `reference-*` のような補助IDを、店内・入口の正式な参照値へ自動変換する仕様も採用していない。今回の参照はワールドが持つエリアIDと元のポータルIDを使う。

## 回帰仕様と実行

```sh
cd game
npm ci --cache /private/tmp/slg-npm-cache
npm run build
npm test
```

`tests/stores.test.ts` は実ワールドを読み取り、次を確認する。

- 棚卸し8棟と現在の施設7件が一致する。建物・施設の改名、削除、追加を見逃さず、外観・施設紐付け・表示名の変化も検知する。
- 各棟が「接続済み」か「店内未対応」に分類され、接続済み店舗とレコードが一致する。新しい店内や入口が追加された場合は、分類とレコードの見直しを促す。
- 架空のテスト用ワールドで正常接続と各不整合を判定する。実マップの定義は編集しない。
- 実際の `Game`・`findPath()`・衝突／遷移処理で開始地点からコンビニに入り、店員の隣へ歩き、向きを合わせて会話する。会話中は固定刻みの全方向入力でも位置が変わらず、終了後に出口から元の屋外玄関前へ戻り、保存・復帰も一致する。

ブラウザ検証は既存 `scripts/e2e.mjs` を変更せず、次を追加する。既存の通常会話表示を使い、購入画面の採用や検証は行わない。将来、店員会話の表示方法を変える場合は、その変更担当がこのブラウザ回帰の表示確認も更新する。

```sh
# 開発サーバー（担当ポート。CIは5173）
npm run dev -- --host 127.0.0.1 --port 5182 --strictPort
# 別ターミナル。sandbox外のブラウザ実行担当に依頼する
SLG_URL=http://127.0.0.1:5182 node scripts/e2e-store-contract.mjs
```

新規E2Eは5項目で、実行時の接続整合、キーボードによる入口通過、実店員への会話／位置固定、元の屋外への帰還、ブラウザ再読込後の復帰を確認する。プレイヤーのテレポートやマップ差し替えは行わない。`SLG_SHOTS` を指定した場合だけ、会話と帰還の画像2枚をそのディレクトリに出力する。自分でサーバーを起動／停止せず、既定URLはCIと同じ5173。CIの `scripts/e2e-*.mjs` の対象になる。

単体・ブラウザ検証に成功しても、未対応の7棟に店内が作られたこと、全店の棚前への到達、利用者のUI承認が済んだことを意味しない。
