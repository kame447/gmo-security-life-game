# マップと探索

状態：舞台設定、分割型マップ構造、屋内外遷移、年代差分、データ契約・命名規則の基本方針は合意済み。描画ライブラリ、タイル寸法、画面解像度、各街区の最終形状・広さ、性能計測の具体的閾値は未決定（提案／要検証）。

## 目的と責務

日本の準都会（地方中核都市の住宅・商業混在地域）を舞台に、プレイヤーが2D見下ろし型のドット絵マップを歩いて探索し、幼少期から高齢期まで同じ町の変化と帰属感を体験できるようにします。

画面全体に一枚絵を収める設計は採りません。町を複数の街区（エリア）およびチャンク／タイルレイヤーに分割し、カメラが主人公を追従して可視範囲を連続描画・必要に応じロードする構造を扱います。参照用の生成画像を引き伸ばしてそのまま使うのではなく、以下の順序で制作・実装を進めます。

1. 画像生成による各街区・屋内の雰囲気検討（見た目の参考画像の作成）
2. 街区・施設・道路・出入口の平面設計（論理マップの作成）
3. タイル・チャンク・オブジェクト等のアセット化と境界の継ぎ目検証
4. TypeScript によるデータ読込・描画・カメラ追従・移動・遷移の実装

## 合意済みの前提

- **舞台**：田舎や山間の村ではなく、日本の準都会・地方中核都市の住宅／商業混在地域とする。低・中層ビル、戸建て住宅、マンション、駅前、商店街、学校、公園、川沿いが自然に共存する町並みを扱う。
- **探索と内部マップ**：プレイヤーは屋外マップを自由に移動し、自宅・学校・店舗などの内部マップに出入りする。自由探索とイベントでの選択を組み合わせて人生を進める。
- **世界の広がりと境界表現**：マップ範囲は有限であっても、幹線道路・線路・水路・建物の遠景などによって町の外へ世界が続く印象を保つ。街区の端を不自然な山や壁で囲わない。
- **ビジュアルの方向性**：2D見下ろし型の親しみやすいドット絵とする。初期のポケモンやカイロソフト作品は体験や空気感の参考であり、固有のグラフィック・素材・画面構成は模倣しない。
- **年代を通じた変化と一貫性**：子ども〜学生〜成人〜中年〜高齢の各年代を通じて同じ町を再訪できる。基本的な道路網と地理は一貫させ、建物・店舗・装飾・NPC・自宅・生活風景の一部が年代や状況に応じて変化する。
- **日常とセキュリティの扱い**：日常イベントとセキュリティイベントの配分目安（7:3〜6:4程度）はイベント側の比率であり、建物数やマップ面積の比率を指定するものではない。危険な場所だけに警告アイコンを表示したり、セキュリティイベントに関わる場所・人物だけを見た目で区別したりしない。
- **実装言語**：TypeScript（TS）を予定する。描画エンジン／ライブラリ、タイル寸法、画面サイズ、各マップの広さなどは根拠のある候補比較と実測によって決定する。

## 1. 世界・地理・動線の設計

### エリア構成と役割

町全体を複数のエリア（街区）に分け、俯瞰した論理マップで配置と接続を設計します。

| エリア候補 | ID例 | 主な役割と風景 | 施設の必須／任意区分 |
| --- | --- | --- | --- |
| 駅前／商店街 | `town-center` | 駅舎、ロータリー、商店街、カフェ、銀行／ATM、交番、低・中層商業ビルが集まる町の中心街区 | 設計時に施設ごとの必須／任意を定義（詳細は提案／要検証） |
| 住宅街・主人公の実家 | `town-residential-west` | 主人公の実家、戸建て住宅、集合住宅（マンション・アパート）、生活道路、近隣の掲示板やゴミ集積所などを含む生活街区 | 実家・自宅は必須、周辺住宅の個別内部は任意 |
| 学校・校庭 | `town-school-north` | 校舎、教室、廊下、校庭、通学路を含む教育・交友の街区 | 子ども・学生期の主要施設として必須 |
| 川沿い・公園 | `town-riverside-park`（仮・要確定） | 河川敷、橋、遊歩道、公園、ベンチなど、年代を問わず立ち寄れる憩い・交流の空間 | 接続動線・交流場所として設計（詳細は提案／要検証） |
| 公共施設／医療 | `town-civic-east`（仮・要確定） | 市役所／窓口、病院・クリニック、図書館・公民館など、手続きや介護・健康に関わる施設群 | 内部マップ有無を含め設計時に区分（提案／要検証） |
| 職場・商業施設 | `town-business-south`（仮・要確定） | オフィスビル、テナント、複合商業施設など、成人期以降の仕事・買い物・転機に関わる街区 | 年代進行に応じた解放・変化を含め設計（提案／要検証） |

※ 上記の `town-center`、`town-residential-west`、`town-school-north`、`home-family-interior` は命名規則の基準例です。未確定のエリアIDや最終的な街区数は平面設計時に確定します。

### 動線と境界の設計要件

- **主要動線の検証**：家→学校、家→駅、商店街→公園などの日常的な移動経路について、道路幅、歩道、横断歩道、建物の入口位置、行き止まりの有無、NPCや装飾による混雑、現在地を把握しやすい目印（ランドマーク）、長距離移動の負担を設計段階で検証する。
- **街区境界の連続接続**：街区の境界は壁や柵で単純に塞ぐのではなく、道路・歩道・水路・線路などが隣接街区へ自然に接続する構造とする。マップ外縁部も、幹線道路の延伸や線路・橋・遠景ビル等によって町の外への広がりを表現する。
- **恒常要素と可変要素の分離**：道路・地形・区画などの恒常的な地理レイヤーと、年代・季節・イベント進行によって差し替える建物・店舗外装・看板・装飾・NPC配置のレイヤー（または差分定義）を分けて管理する。

## 2. 分割マップと画像制作パイプライン

### 構造の階層と責務

単一の巨大PNGをメモリへ常時展開する方式は採らず、以下の階層で責務を分離します。

1. **エリア（Area）**：1つの街区または1つの屋内空間を表す論理単位。隣接エリアとの接続関係や出入口（ポータル）を持つ。
2. **チャンク／タイルレイヤー（Chunk / Tile Layer）**：エリアを一定のグリッドで分割した描画・ロード単位、および地面・建物・前景・衝突などのレイヤー構造。カメラの可視範囲と近傍チャンクのみを描画・ロード対象とする。
3. **画像アセット（Image Asset）**：再利用可能なタイルセット、建物外観、室内タイル、オブジェクト、前景オーバーレイ、背景、または検証済みのチャンク書き出し画像。

### 画像制作と変換のパイプライン

- **見た目の参考画像（リファレンス）の制作**：
  - 駅前街区（`town-center`）を視覚基準とし、住宅街、学校、公園／川沿い、屋内（自宅・教室など）の参考画像を独立して作成する。
  - 全街区で同じ見下ろし視点、縮尺、カラーパレット、建物密度、時代感を統一する。
- **参考画像から実ゲームデータへの変換**：
  - **生成した参考画像は完成タイルやシームレスなマップデータとは見なさない。**
  - 街区間の道路接続、タイル寸法、グリッド配置、ドア（出入口）位置、当たり判定を平面設計図で照合・修正し、タイルアトラスおよびマップ構造化データへ変換する。
  - 隣接するタイルやチャンクを並べた際の**継ぎ目チェック**を必須とする。
- **レイヤーと素材種別の分離**：
  - 屋外地形タイル、建物外観、室内タイル、前景／遮蔽物（キャラクターより手前に描画する屋根・街路樹・標識など）、装飾（家具・小道具）、インタラクト対象、背景を分離して管理する。
  - 参考画像（`assets/images/maps/previews/` 等）、編集可能な原本（`assets/sources/images/`）、ゲーム本体のランタイムが読み込む書き出し画像（`assets/images/` 配下の各カテゴリ）を混在させない。
- **権利と出所の追跡**：
  - 画像生成・編集・書き出しに用いたモデル、ツール、元素材、ライセンス、使用条件、再配布可否を記録し、第三者の著作物を無断またはそのまま流用しない。

## 3. 探索と内部マップ

### 建物の内部区分

マップ上の建物・施設は、体験上の役割に応じて以下の3種類に分類します。

| 区分 | 内容 | 主な対象（優先設計候補） |
| --- | --- | --- |
| 内部あり | 入口から別マップ（室内マップ）へ遷移し、部屋や廊下を歩いて探索・行動できる | 主人公の自宅（玄関・リビング・寝室など）、学校（教室・廊下・校庭など）、主要な店舗・駅・公共施設の一部 |
| 簡易インタラクションのみ | 室内マップへは遷移せず、入口・窓口・ATM・自販機・掲示板などを調べることで会話や選択・取引を行う | 小規模店舗、ATM／端末、バス停、案内板、一部の窓口など |
| 背景のみ | 準都会の街並み密度や生活感を構成するための建物で、内部遷移や個別操作を持たない | 一般の住宅、背景の中層ビル・マンションなど |

### 出入口とマップ間遷移

- 建物の入口／出口、階段、または街区間の接続境界に進入・操作した際、対応する遷移先マップの指定座標と向きへプレイヤーを移動させる。
- 屋内から屋外へ出る際は、入った入口に対応する屋外の復帰位置・向きへ正確に戻す。
- 出入口の判定座標、ドアID、遷移先マップID、復帰位置は、可視画像（ピクセル）に埋め込まず独立した構造化データとして定義する。

### 移動・衝突・重なりとUI競合の制御

- **移動と衝突**：歩行・走行（候補）、壁・柵・家具・進入不可地形との衝突判定、NPCや対象物との接触判定を扱う。
- **前後関係（オクルージョン）**：キャラクターと建物の一部・樹木・家具などの前後関係をレイヤーまたはY座標基準で制御し、自然な重なりを表示する。
- **調べる・会話開始**：プレイヤーの位置と向きから一定距離内のインタラクト対象（NPC、扉、端末、家具、看板など）を判定し、調査や会話を開始する。
- **UIとの入力競合防止**：会話ウィンドウ、選択肢、メニュー、スマートフォン画面などのUIが開いている間はフィールド移動入力を停止し、UI操作と移動操作が競合しないようにする。
- **時間進行との分離**：フィールドの移動や屋内外の出入りだけで勝手に季節や人生の時間が進まないようにする。時間進行の所有者は [遊びの進行](gameplay.md) 側の進行管理とし、探索機能と分離する。

## 4. 年代差分とイベント接続

### 年代による町の変化

- 基底となる道路網・街区構造・地形は全年代で一貫して維持する。
- 年代（子ども〜学生〜成人〜中年〜高齢）や主人公の生活状況（進学、就職、転居、結婚、介護など）に応じて、以下の要素を差分定義によって切り替えられる構造とする。
  - 店舗の開店・閉店・テナントの入れ替わり
  - 建物外観の一部変化、看板・掲示物・街頭装飾の変化
  - 街角や施設内のNPC配置と会話内容
  - 主人公の居住地（実家、一人暮らしの部屋、転居先など）
  - 学校、職場、特定施設への入場・アクセス条件

### イベント管理との疎結合

- **条件評価の分離**：イベントの発生条件をマップ描画や移動ロジックの中にハードコードしない。マップ探索側は「どのエリア・施設・対象物・NPCに対して接触／進入／調査が行われたか」という通知（インタラクト通知）を発行し、現在の年代・能力・資産・交友・職歴・過去履歴・予約状態に基づく条件評価とイベント選定は [イベント共通仕様](events.md) の責務で行う。
- **日常生活に溶け込んだ表現**：自宅でのSNSやネット通販、カフェのWi-Fi利用、駅前での待ち合わせや取引、商店街でのキャッシュレス決済、職場でのメール確認などを、通常の生活行動（場所や対象物へのインタラクション）として扱う。セキュリティリスクのある場所だけに危険マークを出したり、イベント種別が事前に露見する不自然な視覚区別を設けたりしない。

## 5. データ契約・座標系・命名規則

### スキーマ定義の対象

TypeScript による実装に先立ち、以下のデータ契約（スキーマ）を定義します。

| 対象 | 保持する主な情報 |
| --- | --- |
| エリア（マップ）定義 | `areaId`、表示名、屋内外区分、全体グリッド寸法、所属チャンク一覧、隣接エリア接続、背景・環境設定 |
| 施設定義 | `facilityId`、表示名、所属エリア、内部区分（内部あり／簡易インタラクション／背景）、アクセス条件参照 |
| チャンク定義 | `chunkId`（エリア内グリッド座標）、タイル寸法、配置座標、参照アセット／タイルレイヤー、衝突レイヤー |
| 出入口（ポータル）定義 | `portalId`（ドアID）、元エリアID・座標・判定範囲、遷移先エリアID・復帰座標・復帰時の向き、通行条件参照 |
| インタラクション点定義 | `interactionId`、種別（NPC／対象物／端末／入口等）、座標・判定範囲・向き条件、イベント／行動管理へ渡す識別子 |
| 年代差分定義 | `variantId`、適用条件（年代区分・状態フラグ等）、差し替え対象のチャンク／レイヤー／施設状態／NPC配置／ポータル有効性 |

### 座標系と変換規則の一元化

- **座標空間の定義**：
  - **ワールド／エリア座標**：各エリア（街区または屋内マップ）の原点（北西＝左上を `(0, 0)` とする基準案）から東方向を `+X`、南方向を `+Y` とする座標系。
  - **チャンク座標**：エリア内を一定サイズの矩形で区切った非負整数グリッド座標 `(chunkX, chunkY)`。
  - **タイル座標とピクセル座標**：チャンクまたはエリア内のタイル単位座標 `(tileX, tileY)` と、タイル寸法を掛け合わせたピクセル座標 `(pixelX, pixelY)`。
  - **画面（スクリーン）座標**：カメラの位置・ズーム倍率を適用した描画キャンバス上の座標。
- **変換規則の集約**：これらの座標変換とチャンク境界の跨ぎ計算を単一のモジュール／仕様に集約し、チャンク境界通過時や屋内外遷移時に1ピクセルのずれや端数による描画ちらつきが生じないようにする。

### 命名・配置ルール

- **アセット配置先の役割維持**：
  - `assets/images/maps/locations/`：場所（エリア）IDごとの分割チャンク画像・ロケーション画像
  - `assets/images/maps/tilesets/`：地形（`terrain/`）、建物外観（`buildings/`）、室内（`interiors/`）のタイルセット画像
  - `assets/images/maps/backgrounds/`：遠景・外縁背景画像
  - `assets/images/maps/overlays/`：前景・遮蔽物・環境重ね合わせ画像
  - `assets/images/maps/previews/`：街区ごとの見た目の参考画像（リファレンス）・確認用サムネイル
  - `assets/sources/images/`：編集可能な原本データ
  - マップの構造化データ（JSON等）の配置先は、画像素材ディレクトリとは分けて定義する。
- **IDの形式**：
  - エリアID、施設ID、ポータルID等は、永続・一意・意味を持つ英小文字 `kebab-case` とする（例：`town-center`、`town-residential-west`、`town-school-north`、`home-family-interior`）。
  - 画面に表示する日本語名（例：「駅前通り」「実家のリビング」）とデータ上のIDを混同しない。
- **チャンクIDの形式**：
  - エリアIDと3桁0埋めの非負整数グリッド座標で識別する（例：`town-center/chunk-x000-y001`）。
  - 見た目の並び順や一時的な都合でIDを付け替えない。
- **ファイル名と版番号の扱い**：
  - 参考画像・素材・実ゲームデータをファイル名で明確に区別する（例：参考画像は `town-center-reference-v01.png`、実チャンク画像は `chunk-x000-y001.png`）。
  - `-v01` などの版番号は、再生成や比較を行う参考画像・制作検討物にのみ使用し、ランタイムが参照するマップID・チャンクID・実ゲーム用アセット名には版番号を埋め込まない。
- **検証規則の統一**：
  - 画像サイズ、解像度、タイル規格、当たり判定規格、レイヤー描画順、配置JSONの検証規則を仕様書と機械可読なスキーマ／バリデーションで統一する。未確定の数値は「提案／要検証」と明記する。

## 入力と出力

| 種類 | 概念上扱うもの |
| --- | --- |
| 入力 | プレイヤーの移動・方向転換・調べる操作、UI開閉状態、現在の年代・居住地・アクセス権などの状態参照、エリア・チャンク・衝突・出入口・年代差分の定義データ |
| 出力 | カメラ追従による現在位置周辺のマップ・前景・キャラクター描画、更新後のプレイヤー座標・向き・滞在エリアID、屋内外／街区間遷移の結果、イベント・行動管理へ渡すインタラクト通知 |

## 非機能要件と受け入れ条件

実装および総合品質検証において、以下の測定可能な基準を確認します。

- **描画性能**：代表的なデスクトップブラウザ・画面解像度・端末条件を明示して計測する。探索時の目標案は **60fps**（少なくとも指定環境で操作遅延や引っかかりを感じないこと）とし、実装前にフレーム時間・p95・チャンク読込遅延の具体的閾値（提案／要検証）を定めて計測ログで判定する。
- **メモリとロード管理**：単一の巨大一枚絵を常時展開せず、画面外チャンクを無制限にメモリ保持しない。チャンクのキャッシュ上限、近傍プリロード範囲、読み込み失敗時の再試行・フォールバック表示、および長時間探索（チャンク往復）時のメモリ増加が許容範囲内であることをテストする。
- **視覚的一貫性**：全街区・屋内外で同一のタイル寸法・ドット密度・視点・パレット・スケール・レイヤー順序を適用し、チャンク境界の継ぎ目、ぼやけ（滲み）、サブピクセル座標のちらつき、キャラクターと前景の誤った重なりがないこと。ドット絵の不要な補間（スムージング）を無効化する。
- **操作性・アクセシビリティ**：キーボード操作、キーリピート／押しっぱなし移動、壁・角との衝突時の挙動、UI操作中の移動停止、および建物入口や調査対象の視認性を検証する。色だけで通行可否や出入口を伝えない。想定プラットフォーム確定後にゲームパッド／タッチ操作の要否を判断する。
- **決定性と保存・復帰**：エリア切替やチャンクのロード／アンロードによって、位置、向き、適用中の年代差分、NPC・イベント進行、保存状態が不意に変化しないこと。中断／再開後も同じマップ・位置・向き・状態へ正確に復帰できること。
- **堅牢性（ビルド／CI検証）**：欠損画像、遷移先不明の不正な出入口、どこにも接続していない孤立街区、意図しない閉じ込め（行き止まり）、重複ID、不一致なタイルサイズ等はビルド／CIのバリデーションで検出する。ランタイムでの画像読込失敗時にも進行不能・操作不能に陥らないこと。
- **保守性・拡張性**：新しい街区、施設、内部マップ、年代差分を追加する際、既存の TypeScript ロジックに個別マップ専用の条件分岐を増殖させず、データ追加で導入できること。用途の異なる素材とコードを分離し、テスト可能なインターフェースを備えること。
- **ライセンス・容量**：生成・編集元・書き出し素材の出典と権利を追跡可能にする。圧縮方式、配信サイズ、初回ロード時間の測定条件と予算（バジェット）を設計時に定め、公開先の容量・配信制限を満たすこと。
- **検証再現性**：固定のテストマップ、標準テスト経路（家→学校、家→駅、商店街→公園、屋内外の出入りとチャンク往復）、年代条件、端末条件を用意し、回帰テストで接続・当たり判定・出入口遷移・年代差分・イベント通知を再現可能にする。
