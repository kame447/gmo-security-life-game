# 本編のローカル保存の安全性

対象は [Issue #20](https://github.com/kame447/gmo-security-life-game/issues/20)。`main` ceedf04 上の実装候補。保存キーは既存の `slg-map-save-v1` を使う。

## 成否と再試行

`game/src/app/save-store.ts` の `writeSave(data)` は、localStorage の `setItem` が成功した場合に `true`、失敗した場合に `false` を返す。例外で探索を停止させない。従来の呼び出し元は戻り値を無視してそのまま動作する。

`saveStatus()` は独立した状態のコピーを返す。

| 欄 | 意味 |
| --- | --- |
| failed | 読込・書込・検証で失敗しているか |
| reason | 下記の失敗理由。成功時は null |
| pending | 再試行用の有効な JSON がメモリに残っているか |
| retryable | 再試行用の pending があるか。再試行の成功は保存先の状態に依存する |
| changed | 最後の保存試行で、前に観測した値からの外部変更を検知したか |
| backedUp | このセッションで、読めない旧保存の退避を確認できたか |
| lifeProtected | 接続候補でlifeを元のJSONのまま保護したか。trueなら他欄の書込が成功しても新しい人生イベントの進行は未保存 |

失敗理由は `quota-exceeded`（容量超過）、`storage-unavailable`（保存領域へのアクセス拒否・未提供）、`storage-error`（その他の保存先の例外）、`invalid-data`（JSON として損失なく扱えない入力）、`too-large`（指定した上限の超過）、`protected-save`（旧保存を安全に退避できない）に分ける。例外のメッセージや保存内容は状態に含めない。

`retrySave()` は最新の有効な試行の JSON を保存し直す。呼び出し後に元の DTO を変更しても、再試行の内容は変わらない。新しい有効な `writeSave` は古い再試行を置き換え、成功後の再試行は書込を行わない。無効な入力は、先に残っている有効な再試行を置き換えない。

通常保存は一つのキーへの一回の `setItem` とし、失敗時に前の保存を削除しない。読めない旧保存の退避が必要な場合は、先に下記の退避キーへ書く。再試行の記録はメモリ内だけなので、成功前の再読込・タブ終了では失われる。既存の定期保存は、その時点のゲーム状態で再度 `writeSave` を呼ぶ。新しいタイマーや画面での通知は追加していない。

独立したセッションやテストでは `createSaveStore({ storage: () => storage, maxBytes })` を使える。省略時の保存先は localStorage。最上位の四つの関数は既定の一つの store に接続する。

## 欄の保持と旧保存の保護

`game/src/state/save.ts` は既知の位置・外見・資産・スマホを従来どおり修復し、最上位と外見・資産・phone・phone.dataBudget・phone.chat の未知メンバーを保持する。たとえば `assets.layout` や `life`（欄名は仮称）が該当する。既知の配列の内容はその担当 codec が検証・正規化する。壊れた既知の時刻などを「未知欄」として復活させない。

保存安全性の独立候補では `life` の数値・目印・履歴・順序と入れ子の版は不透明なJSONとして保持する。後段の接続候補 `feat/life-local-save` は [人生イベントの保存](life-save.md) のアダプタをGameとDirectorへ接続し、通常の進行を保存する。外側のcodecはraw lifeを運搬し、保護対象lifeは書込直前にも元データを優先する。その場合は `lifeProtected` を返し、LocalSaveSessionは既存の失敗通知へ伝える。外側全体を読めない場合の退避・拒否契約は従来どおり。

`loadSave → Game → writeSave` では、Game が知らない欄を自分の DTO に含めなくても、保存層がその時点の保存済み JSON から未知欄を保持する。再試行時も、元の呼出側の JSON にディスクの最新の未知欄を引き継ぐ。保存へ明示的に新しい未知欄の値を渡した場合は、その値を使う。Game の `serialize()` 単独には未知欄を引き継ぐ責務を加えていない。

最上位 v1・対応する variant だけを読み込み、phone・dataBudget・chat の未来版（数値の v が 1 より大きいもの）は拒否する。`loadSave` は undefined を返して探索を開始できる。最初の書込では、構文破損・未対応版や variant・起動時に読み取れなかった既存保存を、元の文字列のまま `slg-map-save-v1.protected` へ一世代退避してから、新しい進捗を本来のキーへ保存する。書込直前に別タブが壊れた・未来版の保存を置いた場合も同じ扱いにする。退避先に同じ文字列がある場合は退避済みとして保存を続け、別の文字列がある場合は両方を保護して `protected-save` で止める。退避先の読込・書込に失敗した場合も、本来のキーを書き換えず pending を残す。

各書込の前に現在値を確認する。別タブが通常の v1 を書いていた場合は、その最新の未知欄を保持し、既知欄は現在のスナップショットを使って保存を続ける。従来と同じ後勝ちの方式で、検知した外部変更は `changed` で知らせる。未知の life を履歴の内容に従って自動統合する処理は加えない。localStorage のトランザクションや原子的な CAS ではなく、確認と書込の間に生じる別タブの書込まで排他する保証はない。

## 構造と容量

`save-json.ts` は普通の JSON オブジェクト・配列・有限数・文字列・真偽値・null を検証する。Map・Set・Date・クラス・関数・undefined・非有限数・循環・疎配列・アクセサ・Symbol メンバー・深さ64超を拒否し、暗黙の変換や欄の削除で通さない。既知の壊れた単純値は従来の codec で修復したうえで最終 JSON を検証する。

ローカル保存独自のバイト上限定数は設けない。`createSaveStore({ maxBytes })` と `parseSave` の第5引数 `{ maxBytes }` は、呼び出し側の上限を UTF-8 JSON 全体に適用できる。ちょうど上限は受理し、1バイト超過は拒否する。省略時はアプリ独自のバイト上限を加えず、localStorage の実際の書込成否を使う。将来 API と接続する場合は、そこで採用した容量契約の値を渡す。`save-api/` への依存は追加していない。

2026-11-14 の `game/tests/save-size.test.ts` で、既存チャット codec を現行の件数・文字数の上限まで飽和させて計測した結果（最大値の厳密証明ではない）:

| UTF-8 JSON のバイト数 | 日本語280字の各メッセージ | 絵文字280字の各メッセージ |
| --- | ---: | ---: |
| 初期セーブ | 325 | 325 |
| chat | 261,860 | 261,836 |
| phone 全体 | 261,946 | 261,922 |
| life のサンプル | 129 | 129 |
| セーブ全体 | 262,330 | 262,306 |

128 KiB の API 案ではこの既存チャットを拒否する。256 KiB にしても、日本語の例は全体で186バイト超過する。API 担当はこの実測を受け、別ブランチで data 320 KiB を仮値としている。採用値の定義と超過時の契約は API 側に一か所だけ置き、ここでは固定しない。イベント履歴の保持件数や切詰め方は未決定。

## 検証と未決定事項

`save-store.test.ts` は容量超過・アクセス拒否・再試行・最新状態への置換・旧保存の保護・別タブの変更・本編 Game との往復を扱う。`save-preservation.test.ts` は life、資産、外見、位置、スマホと会話、未知欄、構造検証と指定容量の境界を扱う。`save-size.test.ts` は既存チャットと全体のサイズの不整合を再現する。

購入後の保存失敗の再現では、メモリ上は1000円から700円と品1個へ変わり、再試行成功前の再読込は1000円と品なしに戻る。失敗理由と pending を取得でき、保存先が復旧したあとの `retrySave()` で700円と品1個が保存される。購入の取消・確定の扱い、失敗を知らせる画面、未保存のまま終了しようとした場合の扱いは未決定。これらは本編の入口・UI側で、利用者の判断後に接続する。
