# 0014: 列車の確認と到着を分担し、既存のエリア変更通知を使う（試作／要検証）

## 背景

[Issue #36](https://github.com/kame447/gmo-security-life-game/issues/36) は、駅のホームで行き先を選び、明示的に乗車して別の街へ移動する。歩いて踏むだけで発火する出入口とは操作が異なる。一方、到着後の保存や地図には、通常の屋内外移動と同じ現在地を伝える必要がある。

## 今回の判断

- `TrainTravelSession.confirm()` が選択後の確認状態、出発地点・向き・調査対象、路線上の行き先を再検証する。通常の画面はこの経路を通り、選択だけ、または取消では移動しない。
- `main.ts` が渡す到着callbackから `Game.arriveByTrain(destination)` を呼ぶ。Gameは会話中の移動、未登録エリア、整数でない座標、無効な向き、衝突する地点、自動出入口上への着地を拒否する。拒否時は位置と通知を変えない。
- 成功時は歩行を止めて位置と向きを変え、既存の `area-enter` を1回通知する。外見と年代は変えない。入力の解除とフォーカス復帰は共有UIで行う。
- 乗車画面は全体図・外見変更・探索の入力と排他的に扱う。歩行入力や調べる操作、タッチ方向キー、リセットを乗車画面の背後へ渡さない。
- `validateWorld(world, { railLinks })` には明示的な鉄道の有向辺を渡す。検証上も、自動ポータルを追加して鉄道移動を表現しない。

`Game.arriveByTrain` 自体は乗車確認の証明を検証するAPIではない。確認の責務は呼び出し元のセッションにあり、Gameの責務は安全な着地とエリア通知である。通常の実行経路で確認を迂回する呼び出しはなく、確認を強制する新しい型や認可の仕組みは追加しない。

## 理由と採らなかった案

自動ポータルにすると、歩くだけでの乗車や、ホームと線路の構造との不整合を招く。位置の直接代入だけでは、既存のエリア変更通知を受ける保存処理へ到着が伝わらない。列車専用のエリア通知を新設すると、同じ現在地の変更を受け取る経路が増えるため、既存の `area-enter` にそろえる。

ミニマップは実行中のエリアから更新されるため、到着後も同じ現在地を参照する。将来スマホを含む統合版へ取り込む際も、エリア通知と実エリアを用いて位置判定を同期する。現在の配線版にはスマホ・資産・人生履歴の実装がなく、それらの保存互換まで検証したことにはしない。

## 確認と残件

`tests/train-arrival-wiring.test.ts` で実セッションからの選択・取消・確認、通知回数、通知時の位置・外見保存と再読込、無効な着地・会話中の拒否を確認する。既存の世界検証には路線の辺を渡す。`scripts/e2e-train-travel.mjs` では実キーでの往復、取消、保存再読込、ミニマップと乗車画面の排他、3サイズのタッチを検証する。

実ブラウザの実行結果と利用者の実画面でのOKは別途必要であり、この判断記録の追加だけで完成・採用とは扱わない。駅名、隣町の内容、位置とUIは暫定で、運賃・利用条件・時刻表・年代進行は定めない。
